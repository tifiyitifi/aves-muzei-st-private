# Drift database — design

## One connection, opened lazily

```
AppDatabaseProvider.open()
        │  memoised future, retried on failure
        ▼
   AppDatabase (aves.drift.db)
        ├── DriftLocalMediaDb   (LocalMediaDb implementation)
        └── MetaSettingsStore   (SettingsStore v2)
```

Opening is split from the legacy import on purpose: v2 settings must be readable
at `settings.init()`, which runs before `DriftLocalMediaDb.init()` and its
one-time import. A failed open is dropped so the next caller retries; a
successful one is shared for the isolate's lifetime.

## Schema layout

`app_database.dart` aggregates 24 tables only because Drift requires a single
`@DriftDatabase`. Each table, its queries and its row↔model mapping live in the
owning feature's `db/` directory. Adding a capability adds a table and a
migration, not edits spread across a shared schema file.

The column names keep upstream's camelCase (`sourceMimeType`, `stackTileId`,
`createdAt`) because the queries, the legacy import and the reference
implementation all use them.

## Migrations are forward-only and guarded

`onCreate` builds the current schema and its indexes. `onUpgrade` runs each
`MigrationVN` in order. Two rules make a chain of small steps safe:

1. **Guard every structural change.** A database upgrading from v4 passes through
   v7, which creates `wallpaper_groups` with the *current* definition, including
   columns v8/v10/v13 would otherwise add. Those steps check `PRAGMA table_info`
   and skip. Without the guard, SQLite throws "duplicate column".
2. **Rebuild when the key changes.** SQLite cannot alter a unique constraint, so
   v13 renames the old table, creates the new one, copies the rows with
   `surface = 'home'`, and drops the old one.

A step that moves user data preserves the effective value: v11 copies the
pre-v11 global ordering into every group and deletes the key; v14 folds each
lock range into the home pool with surface masks, turning a different lock base
into a lock-only restriction (arithmetically the same range).

## The legacy import

`LegacyImport` reads upstream's `metadata.db` once:

- it imports every table in chunks (text-keyed tables are chunked, not loaded
  whole);
- it commits a cursor per chunk, so a kill resumes instead of restarting;
- it keeps a backup of the legacy file and leaves the original readable;
- a marker in `appMeta` makes it one-shot; a corrupt cursor restarts instead of
  bricking the upgrade;
- a verification mismatch reconciles from a clean slate.

A fresh install has no legacy file: the import marks itself done without creating
one.

## Generated code

`app_database.g.dart` is generated by `drift_dev` and committed. It is part of the
schema: a table change without regeneration compiles against the old shape and
fails at runtime. `build_runner` with `--delete-conflicting-outputs` is the
documented command.

## Anti-patterns

- **Opening a second `NativeDatabase` for a feature.** Use the provider.
- **Adding a column in a migration without the `PRAGMA table_info` guard.** A
  later upgrade through an earlier step already has it.
- **Bumping `schemaVersion` without a `MigrationVN` and a test.** `AGENTS.md`
  forbids it; the app would silently skip a column.
- **Writing to the legacy `metadata.db`.** It is a one-time source, never a
  target.
- **Materializing entries to delete them.** The media DB has a delete-by-id path
  for paged views.
